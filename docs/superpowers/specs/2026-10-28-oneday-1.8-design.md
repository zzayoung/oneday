# OneDay 1.8 — Mobile timeline and quick creation

## Goal

Implement the user's five next-version requests on the existing OneDay Site. Preserve task data, existing scheduling rules, drafts, uploads and the current private audience.

## Interaction decisions

1. The Day timeline header has a visible +. Its dialog exposes `api.createRecord()` so the global + and / keyboard routing can open the same creation sheet above it. Generic creation remains an unscheduled 待办; clicking a time slot retains contextual scheduling. Shortcuts do not trigger while typing, composing, repeating, using a modifier, or while another modal is on top.
2. Coverflow follows the pointer continuously, including depth and rotation where appropriate. Release settles into the nearest cyclic card without rebuilding the selected task editor or resetting the timeline. Keep existing promotion from horizontal browsing into timeline/trash dragging.
3. Task move/resize shows a viewport-clamped start–end time bubble above the dragged card/finger. Ten-minute snap changes produce a short touch-only haptic pulse when the browser supports vibration. Release, cancel and close remove the bubble and dragging state.
4. Touch movement from any task-card area starts dragging after the existing small movement threshold; resize edges retain their role. Empty timeline space remains scrollable. Tap and child expansion remain available.
5. Creation synchronously focuses the content editor within the activation event. Generic delayed modal focus must not steal the selected focus or focus an underlying modal. The category control has exactly four tabs: 待办 / 灵感 / 记录 / 引用. It has no extra category range input. Duration is in the same header row as categories, including on a 390 px phone, with 10–480 minutes, step 10, default 60. Non-action categories keep their existing duration semantics. Save stays 添加.

## Boundaries

- Keep the existing vanilla JS/CSS and shared pointer lifecycle; no new packages.
- Keep immediate local presentation and existing asynchronous persistence.
- Validate browser capabilities once at the interaction boundary; avoid repeated defensive checks for internal typed values.
- Keep cohesive functions; extract helpers for reuse or meaningful interaction boundaries.
- Physical vibration and automatic mobile keyboard appearance depend on browser and operating-system support; no fake success claims.
- QA uses isolated local fixture data. Production data is not used for destructive testing.

## Acceptance

- Regressions exercise shortcut context, focus retention, category/duration state, full-card touch dragging, floating time feedback, vibration ticks and coverflow settle without editor remount.
- Native browser QA checks desktop and 390 px layout, keyboard shortcuts, nested creation, drag/cycle and no horizontal overflow.
- Full existing test suite, production assembly and official Sites build pass before publication to the original project.

Baseline: product 1.7.0, Site version 4, source `e6991cbe6d0e25701f221bf0b13af60e09be5fa2`.
